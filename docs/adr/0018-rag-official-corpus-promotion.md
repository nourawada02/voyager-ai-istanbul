# 0018. Official promotion of the 69-document RAG corpus — `istanbul_rag_B_v2`

- **Status:** Accepted
- **Date:** 2026-08-21

## 1. Scope

Post-submission maintenance checkpoint, not a new Phase 4 checkpoint. Closes a disclosed reproducibility gap (README, prior to this ADR): the 69-document expanded Istanbul corpus (`rag/corpus_sources.py`, already committed) had no repository-provided command that could populate it on a fresh Qdrant volume — the R.1 development shadow collection (`istanbul_rag_B_r1_shadow`) that actually served it in the demo was populated once, by hand, outside any reusable command. This checkpoint makes that reproducible under an official collection name, `istanbul_rag_B_v2`, with no change to the measured retrieval algorithm, chunking, or embedding contract.

## 2. What changed

- `rag/ingest.py` — the stored ingestion fingerprint is now corpus-aware (`compute_fingerprint`): it combines corpus identity (source ids, languages, per-document content checksums, always the canonical full corpus via `load_documents()`), chunking method/configuration, embedding model identity, and a schema version. Previously it was a pure function of chunking/embedding configuration only, which is why the original 20-document collection and the 69-document expansion silently shared one fingerprint.
- `rag/ingest_cli.py` — `status`/`bootstrap` (the two working subcommands; see §4 for `ingest`) target a configurable `--collection-name` / `QDRANT_COLLECTION_NAME`, defaulting to `istanbul_rag_B_v2`. `docker compose run --rm rag-ingest bootstrap` on a genuinely empty Qdrant volume reproducibly populates it: 69 documents, 287 chunks, 288 total points (chunks + one fingerprint marker).
- `docker-compose.yml`, root `.env.example`, `services/istanbul-expert-b/phase4/config.py`, `services/istanbul-expert-b/.env.example` — the write path (`rag-ingest`) and read path (`agent-system-b`) share the same `QDRANT_COLLECTION_NAME` variable and default, so a fresh clone's bootstrap populates exactly what System B reads.

## 3. Legacy collections are preserved, not migrated

`istanbul_rag_B` (91 points, the original frozen 20-document Phase 3 production collection) and `istanbul_rag_B_r1_shadow` (288 points, the R.1 development shadow collection this checkpoint formally supersedes) are never deleted, renamed, or mutated by this checkpoint's code or tests. Both remain queryable rollback/evaluation artifacts by setting `QDRANT_COLLECTION_NAME`/`QDRANT_EXPECTED_FINGERPRINT` back explicitly. Enforced two ways:

- **Fingerprint fail-closed, structurally.** The new corpus-aware algorithm produces a different fingerprint than the legacy collections' own stored marker (computed under the old, corpus-blind algorithm) by construction — any write attempt against either legacy name immediately hits `fingerprint_mismatch` and refuses.
- **Explicit deny-list on the one destructive path.** `--rebuild-on-fingerprint-mismatch` (the only code path in this module that can call `delete_collection`) refuses outright — before any network connection is even attempted — whenever the resolved `collection_name` is `istanbul_rag_B` or `istanbul_rag_B_r1_shadow` (`ingest_cli.PROTECTED_LEGACY_COLLECTIONS`), regardless of whether that name arrived via the default, `--collection-name`, or `$QDRANT_COLLECTION_NAME`. Proven both hermetically (an unreachable `qdrant_url` still refuses, showing no connection was needed) and against the real live demo Qdrant instance's real legacy collections (point count and fingerprint marker identical before/after).

## 4. Incremental ingestion is disabled for this release

The official collection's stored fingerprint represents *exactly* the canonical 69-document corpus, and `rag/ingest.py::compute_fingerprint()` (by design — see §2, and the fix for the incremental-add regression it itself caused during this checkpoint's own development) always computes that fingerprint from the full canonical corpus (`load_documents()`), never from whatever partial `documents=` a given `ingest_config()` call is actually asked to embed. That is exactly why a naive "just refuse against `istanbul_rag_B_v2`, allow it elsewhere" fix (this ADR's own first draft) was insufficient: pointed at any *other*, noncanonical collection name, the same `ingest --source` code path would still call `ingest_config()` with a partial document set and still receive — and store — the canonical 69-document fingerprint back, so a one-document collection could end up indistinguishable from the real thing by `status`.

Rather than build a second, parallel fingerprinting scheme for "canonical collection plus N incremental documents" within this checkpoint's scope, `rag/ingest_cli.py ingest --source PATH` is **disabled outright for this release**: it refuses unconditionally, for every collection name (including `istanbul_rag_B`, `istanbul_rag_B_r1_shadow`, and `istanbul_rag_B_v2` explicitly), before loading any file or opening any Qdrant connection — mutating nothing, ever, regardless of arguments. `cmd_ingest`'s body is now a single unconditional refusal (`DISABLED_INGEST_SOURCE_MESSAGE`); the demo-document validation helpers it used to call (`_load_demo_documents`, `DocumentRejected`) remain defined and unit-tested in isolation, ready to be reused by a future, correctly-fingerprinted versioned-ingestion design, but are no longer reachable from any CLI command.

To add sources under this release: define a new, explicitly versioned corpus manifest (extend `rag/corpus_sources.py`'s `DOCUMENTS`, or add a new manifest alongside it) and `bootstrap` a new, separately named versioned collection from it (`--collection-name` / `$QDRANT_COLLECTION_NAME`) — never `ingest --source` against an existing one. `bootstrap`'s own subcommand accepts no `--source`-shaped argument at all, so it structurally cannot be given partial content; the only way to write the official fingerprint through this CLI's reachable surface is to genuinely ingest the full corpus `bootstrap` always loads.

## 5. Verification

Against two independent disposable Qdrant instances (separate containers/ports, never the shared demo volume, torn down afterward): `bootstrap` on a genuinely empty instance produced exactly 69 documents / 287 chunks / 288 points both times, `status` reported `ready` with the expected fingerprint, a second `bootstrap` run was a verified no-op (idempotent), and one EN/TR/AR retrieval each returned real, grounded citations both times. `ingest --source` against `istanbul_rag_B_v2` on the live disposable instance was confirmed refused (exit 2) with the point count unchanged at 288. Two dummy collections literally named `istanbul_rag_B` and `istanbul_rag_B_r1_shadow` were created on a disposable instance specifically to prove `--rebuild-on-fingerprint-mismatch` refuses them even with real, mismatched content present (both remained at their original 1-point dummy-fingerprint-marker state, never deleted or rebuilt). The live demo Qdrant instance's two real legacy collections were confirmed byte-for-byte unchanged (collection list, point counts, fingerprint markers) before and after all of this checkpoint's work, across all three review rounds and their full test suites.

## 6. Not in scope

No retrieval, generation, or routing metric was re-measured. The existing 88.9% RAG-origin figure (`EVALUATION.md` §6) was measured against the R.1 shadow collection's corpus content — the same content `istanbul_rag_B_v2` now serves under its official name — and is not re-claimed as having been re-run against the new collection. No submodule pointer bump, no commit, and no push are part of this checkpoint; it stops before staging.
