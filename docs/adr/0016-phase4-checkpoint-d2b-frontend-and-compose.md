# 0016. Phase 4 Checkpoint D.2B — Streamlit frontend, explicit fixture mode, and five-service Docker Compose

- **Status:** Accepted.
- **Date:** 2026-08-18

## 1. Scope

This is the final major construction checkpoint. Builds the real `chatbot-ui` Streamlit frontend inside `services/frontend`, an explicit deterministic demo/fixture mode at the System A composition boundary, and a real root `docker-compose.yml` bringing up exactly the five long-running services architecture.md §4.1 requires — `agent-system-a`, `agent-system-b`, `mcp-server`, `vector-db`, `chatbot-ui` — with no sixth service, no MongoDB/PostgreSQL/Redis/Celery/Kafka/Kubernetes/auth/payment/booking service ever added. The final README/EVALUATION rewrite and Phase 6 evaluation work remain explicitly deferred past this checkpoint (§8).

## 2. Frontend ownership and why it only calls System A

`services/frontend/phase6/` is entirely new, self-contained code inside the existing frontend submodule — never importing `orchestration`, `providers`, `phase1`, or `phase4` (unlike `orchestration/system_a/`, which legitimately imports across the root/submodule boundary as the composition root). This is a deliberate, structural choice, not just a convention: the frontend's only network dependency is `phase6/api_client.py::SystemAClient`, which speaks only to `AGENT_SYSTEM_A_BASE_URL` — there is no code path anywhere in `phase6/` capable of reaching a provider, Travel MCP, Qdrant, or System B directly, matching the fixed topology's own "chatbot-ui → agent-system-a" edge exactly. `phase6/results.py` (pure, Streamlit-free extraction/formatting over a validated System A `final_result`) is kept separate from `phase6/app.py` (thin UI glue) specifically so the non-trivial defensive-rendering logic is unit-testable without Streamlit's own test harness.

**Packaging — no PYTHONPATH/sys.path anywhere in `phase6/`, mirroring §7's rule for `agent-system-a`:** `services/frontend/pyproject.toml` (new, minimal, `packages = ["phase6"]`) makes `phase6` a real installed package — `services/frontend/Dockerfile` runs `pip install --no-deps .` before `streamlit run phase6/app.py`, and the same editable install (`pip install -e .`) is used locally for pytest/AppTest. This is the declared mechanism `phase6/app.py`'s own `from phase6 import ...` imports rely on. A real defect was found and fixed during this checkpoint's own iteration: `streamlit run phase6/app.py` (the actual Docker `CMD`) adds only the script's own directory (`/app/phase6`) to `sys.path`, not its parent (`/app`) — causing a genuine `ModuleNotFoundError: No module named 'phase6'` inside the real container that every hermetic test missed (pytest/AppTest resolve modules differently, from `services/frontend` as the working directory). The first fix attempted was a `sys.path.insert(...)` bootstrap at the top of `app.py` — this was **removed** once identified as exactly the "no production sys.path/PYTHONPATH hack" pattern this project forbids, and replaced with the real package install described above. `phase6/tests/test_packaging.py` is the regression guard: it proves `phase6` imports successfully from a subprocess started in an unrelated directory with `PYTHONPATH` explicitly removed (possible only because of the real install, never a working-directory coincidence), cross-checks the installed distribution via `importlib.metadata`, and statically asserts `phase6/app.py`'s own source contains no `sys.path`/`PYTHONPATH`/`import sys` text at all.

## 3. Request/result contracts reused, not invented

The trip-request form maps to `TripRequestInput`-shaped JSON matching `POST /v1/runs`'s existing Checkpoint D.2A contract (`origin`/`destination`/`depart_date`/`return_date`/`traveler_count`/`budget`/`preferences`) — the frontend never invents a competing shape, and never needs to import `phase1.models.TripRequest` to stay correct, since the wire contract is just JSON. `phase6/results.py` reads exactly the `final_result` shape `phase4.graph` already produces (`{"status","observations","warnings","narrative"}` or the degraded/cancelled variant), including the `_UNWRAPPED_ACTIONS` distinction (`search_stays`/`estimate_fair_price`/`call_istanbul_expert` are not `ProviderResponseEnvelope`-wrapped — ADR 0009 §5 / ADR 0014 §3) already established and tested at the orchestration layer.

## 4. SSE and session behavior

`SystemAClient.stream_events` is a small, local, spec-literal SSE parser (`id:`/`event:`/`data:`, blank-line-terminated, `:`-prefixed heartbeats ignored) matching `orchestration/system_a/sse.py::format_event`'s exact wire format — never a third-party SSE client library. Because Streamlit has no native background-task/websocket primitive the app can rely on, `phase6/app.py` performs **one bounded read per script rerun** (`_pull_new_events`, capped at ~2s or a terminal event, whichever comes first) rather than consuming the whole stream in one blocking call — this keeps the "Cancel this run" button interactable between reruns at the cost of a few hundred milliseconds of polling latency, an explicit, documented trade-off appropriate for a local academic demo, not a production low-latency requirement.

`run_id`/`session_id` persist in `st.session_state` for the lifetime of the browser session; reconnecting (a page reload while a run is still `pending`/`running`) re-fetches current status via `GET /v1/runs/{id}` before resuming the bounded polling loop, so a stale client never shows outdated progress. Retrying always calls `create_run` again for a brand-new `run_id` — `_reset_for_new_trip` only clears local `st.session_state`, never mutates or deletes a prior run's server-side history. A per-attempt `idempotency_key` (`uuid4`, regenerated on every reset) is sent on every `create_run` call as defense-in-depth on top of the structural protection `st.form` + run-id-gated rendering already provide (the trip form is not even rendered once a run exists, so there is no later rerun that could re-submit it).

## 5. Fixture versus real mode

`orchestration/system_a/config.py::system_a_mode()` reads `VOYAGER_SYSTEM_A_MODE`: absent or `"real"` → the unchanged Checkpoint D.1 pair (`ProductionToolExecutor` + `QwenDecisionProvider`); exactly `"fixture"` → `phase4.tools.FakeToolExecutor` (already-existing, production-owned, Checkpoint D.0 deterministic executor, reused unchanged) + the new `FixtureDecisionProvider` (Checkpoint D.2B). Any other explicit value raises `SystemAModeConfigurationError` before the app is even built — there is no silent coercion in either direction. `orchestration/system_a/entrypoint.py` is the single place this selection happens for the real deployed service; every hermetic test builds its own app via `create_app()` with directly-injected fakes and never reads this variable at all.

**Two distinct, explicit defaults, never conflated:** `config.py::system_a_mode()`'s *own* default — what a bare standalone process (or a hermetic test) sees when the variable is entirely absent from its environment — is `"real"`, matching every prior checkpoint's behavior before this variable existed. Root `docker-compose.yml` supplies a *separate, Compose-level* default on top of that: `VOYAGER_SYSTEM_A_MODE: "${VOYAGER_SYSTEM_A_MODE:-fixture}"` means an operator running `docker compose up` with no `.env` file gets `"fixture"` injected into the container's environment — indistinguishable, from `system_a_mode()`'s own point of view, from the operator having typed `VOYAGER_SYSTEM_A_MODE=fixture` themselves. Neither layer silently falls back to the other's default; each is its own explicit, documented choice (`config.py`'s docstring and `docker-compose.yml`'s own header comment both state this precisely). Real-provider mode under Compose requires an operator to set `VOYAGER_SYSTEM_A_MODE=real` *and* supply `QWEN_API_KEY`/`QWEN_BASE_URL`/`SERPAPI_API_KEY` through a real, never-committed `.env` file — never a default, always an explicit opt-in.

`FixtureDecisionProvider` (`orchestration/system_a/fixture_decision_provider.py`) is new, small, explicit, rule-based routing code — not a duplication of existing business logic (no deterministic "which tool next" policy existed anywhere before this checkpoint; Qwen decides that in real mode, and test-only `ScriptedDecisionProvider` helpers only ever replay one fixed script for one test, never a general policy over an arbitrary real trip request). It satisfies `phase4.qwen_client.DecisionProvider`'s exact protocol and reads the same prompt payload `phase4.graph._build_decision_prompt` already builds, so it plugs into the unmodified bounded LangGraph loop through the same seam Checkpoint D.1 established — no graph, guard, or bound was touched. It deliberately proposes `get_weather → search_flights → search_stays → call_istanbul_expert → synthesize` and skips `estimate_fair_price`/`web_search`: both are optional, and `estimate_fair_price`'s `stay_id` argument has the identical "the decision provider never actually sees a real stay id" limitation in REAL mode too (`orchestration/system_a/tool_executor.py::_validated_stay_id` only ever forwards a server-validated id) — fixture mode is not cutting a corner real mode does not already have.

`/health` gained a non-secret `mode` field (`"real"`/`"fixture"`), passed through explicitly by `create_app(..., mode=...)` — the frontend's health banner reads this and shows a clear "🧪 Demo / fixture mode" notice whenever it is `"fixture"`, satisfying "the UI must clearly label fixture/demo mode when the API exposes that non-secret operational fact" without the frontend ever guessing from behavior. The API, SSE mechanism, SQLite persistence layer, and frontend code are identical in both modes — only the two capability objects differ.

## 6. Five-service Compose topology, volumes, and service discovery

```
chatbot-ui  ->  agent-system-a  ->  mcp-server
                       |
                       v
                agent-system-b  ->  vector-db
```

Every cross-service URL in `docker-compose.yml` uses the internal Compose service name (`http://agent-system-a:8002`, `http://mcp-server:8001`, `http://agent-system-b:8000`, `http://vector-db:6333`) — never `localhost`, which would resolve to the calling container itself. `depends_on` uses `condition: service_healthy` throughout, so a dependent service's container is created but does not receive traffic-generating requests until its dependency's own `HEALTHCHECK` passes.

Two named volumes matter for this checkpoint: `agent_system_a_data` (System A's `RunStore` SQLite file plus the LangGraph checkpoint tables, Checkpoint D.2A) and `qdrant_storage` (Qdrant's own on-disk index). A third, `agent_system_b_data`, persists System B's ADK session store and optional embedding-model cache across restarts — pre-existing to that service's own Dockerfile, not new here. Verified directly: `docker compose restart agent-system-a` followed by `GET /v1/runs/{id}` for a run created before the restart still returns `status: "completed"` with all four original observations intact (§9).

`agent-system-a` and `mcp-server` build from the **repository root** as their Docker context (`context: ., dockerfile: orchestration/system_a/Dockerfile` / `services/travel-mcp/Dockerfile`) — a deliberate, necessary change from the prior Phase 1 skeleton's per-submodule contexts. `agent-system-a` needs this because it is the real Checkpoint D.2A production service, which imports `providers/`, `orchestration/`, and `services/planner-a`'s `phase1`/`phase4` through the real declared `pyproject.toml` dependency path (§7); `mcp-server` needs it to bake in the real, already-generated (never retrained here) Checkpoint C.1/C.2 accommodation dataset/manifest/ML bundle/district registry, which live at the superproject root, not inside `services/travel-mcp`. `agent-system-b` and `chatbot-ui` remain self-contained, per-submodule build contexts — neither needs anything outside its own directory.

## 7. Packaging: no PYTHONPATH/sys.path restoration

`orchestration/system_a/Dockerfile` installs the real declared dependency path Checkpoint D.2A's root `pyproject.toml` already established: `pip install -r orchestration/requirements.lock` then `pip install --no-deps -e .`, after copying in exactly `pyproject.toml`, `providers/`, `orchestration/`, and `services/planner-a/phase1`+`phase4` (never the whole `planner-a` submodule, never `rag/`). No `PYTHONPATH` environment variable and no `sys.path` mutation appears anywhere in this image. One real defect was found and fixed while building this image for the first time: `orchestration/requirements.lock` (Checkpoint D.2A) had accidentally pinned `pywin32==312` unconditionally — a transitive dependency `mcp` itself declares with a `sys_platform == 'win32'` marker, correctly resolved on the Windows host that originally generated the lock file, but incorrectly re-emitted without that marker, making it uninstallable on the Linux-based production image. Fixed by removing the line with a documented explanation, not by guessing a replacement version.

## 8. Qdrant population limitation

`vector-db` starts as a real, empty Qdrant instance — this checkpoint never runs ingestion itself, and does not invent a sixth long-running container to do so. `QDRANT_URL` defaults to empty in `docker-compose.yml` (matching `services/istanbul-expert-b/Dockerfile`'s own pre-existing safe default) rather than being pointed at `vector-db` unconditionally: simply setting `QDRANT_URL` makes System B synchronously download and warm its pinned multilingual embedding model before accepting any connection at all — a real, internet-dependent, multi-minute cold start, encountered directly while first bringing this stack up in "offline fixture" mode (§9's original attempt hung for minutes with `agent-system-b` stuck in `health: starting`, root-caused, and fixed by leaving `QDRANT_URL` unset by default rather than always-on). Real citation-bearing RAG results require the operator to run Phase 3's existing, frozen, out-of-band ingestion pipeline once against `http://localhost:6333` while this stack is up, then set `QDRANT_URL=http://vector-db:6333` explicitly (a real `.env`, never committed) before restarting `agent-system-b`. `RAG_REQUIRED=false` remains the default either way — System B degrades to catalog-only scheduling with an explicit warning, exactly as Checkpoint B already proved, never a hard failure.

## 9. Verified end-to-end evidence (fixture mode, real Docker containers)

All five containers reached `healthy` within seconds of `docker compose up -d` (after the QDRANT_URL fix, §8): `vector-db`, `mcp-server`, `agent-system-b` (`degraded_reason: "qdrant_url_not_configured"`, honest and expected), `agent-system-a` (`mode: "fixture"`), `chatbot-ui`. A real trip was submitted via `POST http://127.0.0.1:8002/v1/runs`; the real SSE endpoint streamed `run_started → action_started/action_completed ×4 (get_weather, search_flights, search_stays, call_istanbul_expert) → run_completed`; `GET /v1/runs/{id}` returned a terminal, schema-valid `status: "completed"` result. `docker compose restart agent-system-a` followed by the same `GET` call proved the completed run survives a full container restart. `docker compose down` stopped all five containers cleanly with no stragglers (`docker compose ps -a` empty afterward; `docker ps` system-wide also showed exactly the expected containers throughout, never a sixth). Exactly zero real Qwen/SerpApi/paid-provider calls were made anywhere in this evidence — `mode: "fixture"` was confirmed at `/health` before the trip was submitted.

## 10. Remaining Phase 6 work explicitly deferred

The final README/EVALUATION.md rewrite, the architecture diagram, the backup recording, and the formal Phase 6 evaluation suite (architecture.md §17's own Phase 6 gate: "Full evaluation + failure analysis first") are explicitly **not** done in this checkpoint — this checkpoint builds the UI and container topology those deliverables will document, but does not itself produce the evaluation report. A real browser-rendered visual check of the Streamlit UI was also not performed (no browser automation framework was added, per this checkpoint's own "no heavy browser framework" instruction) — the frontend's rendering/extraction logic is instead covered by 47 hermetic tests (`streamlit.testing.v1.AppTest` + pure-function tests over realistic fixture data), and the real container was confirmed to serve its page (`HTTP 200`, clean startup log) without error.
