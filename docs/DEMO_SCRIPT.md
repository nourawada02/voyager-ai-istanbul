# VoyagerAI Istanbul — 5-Minute Demo Script

A timed walkthrough of the committed system, real mode (`VOYAGER_SYSTEM_A_MODE=real`), all five containers running via `docker compose up -d`. Full architecture reference: [`README.md`](../README.md). Evaluation evidence referenced verbally in this script: [`EVALUATION.md`](../EVALUATION.md).

**Before presenting:** confirm real credentials are set in `.env` (`QWEN_API_KEY`/`QWEN_BASE_URL`, `SERPAPI_API_KEY`), the stack has been running long enough for System B's one-time embedding-model warmup to finish (`docker compose ps` shows `agent-system-b` already `healthy`, not still starting), and at least one earlier session already exists and is visibly `degraded` in the sidebar (used in the 4:30–5:00 segment — see that segment for how to produce one ahead of time if none exists yet).

## Tested primary trip (use these exact values)

| Field | Value |
|---|---|
| Origin | `BEY` |
| Departure date | 5–10 days from the demo date |
| Return date | a few days after departure |
| Travelers | 2 |
| Budget | `60000 TRY` |
| Interests | history, culture, food |
| Pace | moderate |
| Language | English |

This exact combination is the one used to validate this script; do not substitute a different origin/budget/interest combination for the live run.

## Five interactions (the entire live sequence)

1. Submit the trip form with the values above.
2. `What is my budget?`
3. `Why did you recommend Chora Church?` — if Chora Church is not one of the points of interest this particular run actually scheduled (check the Itinerary tab first), ask about whichever point of interest the dashboard *did* display instead; do not ask about a POI not shown on screen.
4. `ما هي ميزانيتي؟`
5. `Change my budget to 50000 TRY.`

**Only one modification/replan happens in this sequence — step 5.** No other step creates a new run.

## 0:00–0:30 — Architecture and five healthy containers

Say: *"VoyagerAI Istanbul is a decision-support trip planner — it never books, reserves, or pays for anything. Two independently deployed agent systems, one shared MCP tool service, one vector database, one chat UI — five containers, talking only over the boundaries shown here."*

Show the architecture diagram in [`README.md`](../README.md#architecture), then run:

```bash
docker compose ps
```

Point out all five report `healthy`: `agent-system-a`, `agent-system-b`, `mcp-server`, `vector-db`, `chatbot-ui`. Open `http://localhost:8501`.

## 0:30–2:00 — English trip-plan route (Interaction 1)

Submit the trip form with the exact values in the table above.

Say while the SSE progress log streams: *"This is the bounded LangGraph ReAct loop — a supervisor delegates to an internal Travel Search specialist for flights, stays, and weather, then calls System B, a separate Google ADK agent, over a real A2A network call, for the day-by-day itinerary."* Point at each `action_started`/`action_completed` line as it appears.

When the run completes, open the **Flights**, **Stays & fair price**, and **Itinerary** tabs — note the fair-price deal score and the historical-snapshot disclaimer on accommodation. Note which points of interest the Itinerary tab actually shows, for Interaction 3 below.

## 2:00–3:00 — RAG-backed recommendation and cited explanation (Interaction 2)

Scroll to **Continue planning** below the dashboard.

**Interaction 2:** `What is my budget?`

Point out: the answer states the exact stored amount and currency, and no new run is created — this is a deterministic answer read directly from the stored trip, not a model call.

**Interaction 3:** `Why did you recommend Chora Church?` (or the actually-displayed point of interest, per the note above)

Say: *"The explanation is generated by Qwen but constrained to the completed run's itinerary and retrieved source evidence; it does not launch a new travel search, MCP call, or A2A planning request."* Open the **Sources** tab and point at the citations. Mention: *"Across our own measured demo cases, 88.9% of scheduled points of interest come from real retrieval, not the static catalog — see EVALUATION.md §6."*

## 3:00–4:00 — Arabic response and budget alteration (Interactions 4–5)

**Interaction 4:** `ما هي ميزانيتي؟`

Say: *"This is answered deterministically from the stored trip, in Arabic — no model call for a plain factual question."*

**Interaction 5 (the sequence's one modification):** `Change my budget to 50000 TRY.`

Point out: the assistant states the new amount correctly in major currency units, exactly one new run is created, the same session ID is kept (visible in the run header), and the dashboard updates in place.

## 4:00–4:30 — Sidebar session switching and persistence

Open the **Recent trips** sidebar. Say: *"Every session ever planned in this database is listed here, most recently updated first, with a deterministic title — never model-generated."*

Click a **different**, earlier session in the sidebar (planned before this demo, or in a previous segment of the same demo). Point out: the dashboard and chat transcript both switch completely (no merged messages), with no new run created. Click back to the session just demoed — its full transcript is exactly as left, no duplication.

Mention: *"This is backed by SQLite, on a named Docker volume — it survives a `chatbot-ui` restart, which we verified directly during development."*

## 4:30–5:00 — Controlled degradation (already-saved session) and architectural recap

**Do not stop any container during the live demo.** Instead, open an **already-saved, previously-degraded session** from the sidebar (prepared before presenting — see below) and point at its **Warnings** panel: *"This session's run genuinely could not reach one provider when it ran — the system reported that honestly instead of inventing a result. That's a `degraded`, not a `failed` or fabricated, outcome."*

**Preparing that saved session ahead of time (do this once, before presenting, not live):** briefly stop one dependency, submit a trip, let it finish `degraded`, then restart the dependency —

```bash
docker compose stop mcp-server
# submit one trip through the UI; wait for it to reach "degraded"
docker compose start mcp-server
```

That session then remains in the sidebar, ready to open live at 4:30 without touching any container during the timed presentation.

**Lower-risk live alternative** (if no pre-saved degraded session is available): in chat, on the current session, type `Move my departure to yesterday.` This deterministically returns a `clarify` response rejecting the invalid date — no container manipulation needed, and it still demonstrates honest, non-fabricated handling of an invalid request instead of a provider failure.

Close with: *"Every bound in this system — the 8-call tool budget, the 60-second deadline, the closed action allowlist — is enforced in code, not just in a prompt. And when something really does fail, the system says so honestly instead of inventing an answer."*

### Appendix: full container-stop degradation procedure (recorded backup / rehearsal only — never in the live timed path)

```bash
docker compose stop mcp-server
# submit a new trip through the UI; observe it reach "degraded" with an
# accommodation-search warning instead of a crash or a fabricated stay
docker compose start mcp-server
```

Use this only to *prepare* the pre-saved degraded session ahead of time, or to record a standalone backup clip — never live during the timed 4:30–5:00 window, since restarting a dependency mid-presentation risks a longer outage than the time budget allows.
